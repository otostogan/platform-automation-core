# Platform Automation Core v0.4.0

Makes redeploying an earlier release actually redeploy it, and reclaims the
disk that superseded releases used to hold forever.

Release assets:

- `otostogan-platform-0.4.0.tar.gz` — Ansible Collection
  `otostogan.platform`.
- `platform_automation_runtime-0.4.0-py3-none-any.whl` — Python runtime and
  controller utilities.
- `SHA256SUMS` — integrity checks for both installable artifacts.

Changes:

- Deploying a release tag that already had a ledger record took a shortcut: it
  pulled the image and materialized secrets but never started containers, then
  reported `containers_started: true` because that field was read from the
  stored record's status rather than from what the invocation did. Deploying an
  earlier revision to roll back therefore reported success while the newer
  release kept running. The shortcut now applies only when the matched record
  is the release that is currently deployed, where a rerun is genuinely a
  no-op and says so. Any other match is a new deployment: it gets its own
  ledger record chained to the current release, and it starts containers. The
  guard that a release tag may not point at a different image or bundle is
  unchanged.
- Rolling back through the application's own deploy workflow is now the normal
  path, and the ledger records it as forward history. `platform rollback`
  remains the host-side path for when CI, the registry, or the network is
  unavailable.
- Successful deployments and rollbacks now reclaim superseded artifacts.
  Retention keeps the newest distinct image digests — not the newest
  deployments — so redeploying one version repeatedly never evicts the versions
  behind it. Within that depth a release stays rollback-able with no network.
  Ledger records are never pruned.
- An image digest is removed only when no ledger on the host still wants it,
  because environments of one application routinely run the same digest.
  Removal is per-reference; the platform never runs `docker system prune`,
  which would take the proxy and its ACME companion with it.
- Decrypted runtime secrets are now kept only for the running release. Rollback
  and reboot recovery both re-materialize them from the staged bundle, so the
  older copies were exposure without purpose.
- Retention runs after the ledger is committed and can only warn. A deployment
  that succeeded is never reported as failed because housekeeping was not.

Contract:

- `deployment.retained_releases` is a new optional `platform/v1` field, an
  integer from 1 to 50, defaulting to 5. Existing manifests stay valid and get
  the default. A manifest that sets it needs this release or newer.

Ledger:

- Release timestamps now carry milliseconds. Release order is derived from
  them, and two deployments can land inside the same second — which left the
  order undefined, and reboot recovery refuses to act on an ambiguous order.
  The fractional part is optional in the schema, so records written by earlier
  releases remain valid and need no migration.
