# Platform Automation Core v0.6.0

Makes `database.mode: docker` mean something: the platform now runs the
database an application declares.

Release assets:

- `otostogan-platform-0.6.0.tar.gz` — Ansible Collection
  `otostogan.platform`.
- `platform_automation_runtime-0.6.0-py3-none-any.whl` — Python runtime and
  controller utilities.
- `SHA256SUMS` — integrity checks for both installable artifacts.

Changes:

- A new `database_runtime` module generates a PostgreSQL Compose model on the
  host under `/var/lib/platform/databases/{project}/{environment}/`. The
  application states only the major version; the platform decides the image,
  the volume, the network, and the credential. The generated model is host
  state, like the release ledger — never part of a bundle.
- The image tag `postgres:{major}` is resolved to a digest exactly once and
  pinned until the manifest's major changes, so a minor update is a
  deliberate act rather than a side effect of a redeploy.
- The volume and network carry one deterministic name per project and
  environment. The volume survives deploys, rollbacks, and release
  retention; the network is internal and never published. The application
  reaches the database through the `PLATFORM_DB_NETWORK` interpolation, so
  its compose file stays environment-agnostic, and the contract validator
  now enforces that a docker-mode application joins that network — and that
  an external-mode application does not reference it.
- The credential is generated on first deploy and stored SOPS-encrypted to
  the same age recipients as the application's own secrets, escrow included,
  so the database password inherits the bus factor of everything else. Its
  envelope is re-encrypted whenever the application's recipient set changes;
  the password itself does not rotate. `DATABASE_URL` is injected beside the
  application's secrets; an application that ships its own is refused as a
  contradiction.
- Deploy order: the database must be up and healthy before migrations run,
  before the application starts, and before the ledger records a release. A
  database that will not come up fails the deploy with nothing swapped and
  nothing recorded. Rollback and the no-op redeploy path ensure the database
  the same way.
- Boot recovery re-materialises the tmpfs database material — the injected
  `DATABASE_URL` and the container's bootstrap environment — without
  touching Docker; the container itself restarts from its baked
  configuration.

No changes for applications with `database.mode: external`.
