# Platform Automation Core v0.16.1

The host checks the application's health path itself before switching
traffic; the console dispatches deployments.

Release assets:

- `otostogan-platform-0.16.1.tar.gz` — Ansible Collection
  `otostogan.platform`.
- `platform_automation_runtime-0.16.1-py3-none-any.whl` — Python runtime and
  controller utilities.
- `SHA256SUMS` — integrity checks for both installable artifacts.

Changes:

- `platform deploy` now requests `service.healthcheck.path` on the new web
  container — its `platform-edge` address, the first domain as `Host` —
  until it answers 2xx or 3xx or `timeout_seconds` runs out, after
  `compose up --wait` and before nginx is switched. A release that starts
  but does not answer is refused and rolled back like one that never
  started, and the ledger says so. Until now that path was checked only by
  the deployment workflow's last step, after the release was already
  recorded as deployed; the first deployment of a new application was
  recorded healthy while answering 404. `rollback` and reboot recovery use
  the same start path and get the same guard.
- The operator console's Deploy action runs: latest release or a tag, the
  branch the tailnet credential is bound to, the exact `gh workflow run`
  shown and confirmed (typed for production), the run watched to the end,
  then `status` from the host.
- `platform update` reads the image name from any `env:` mapping and keeps
  the application's existing `tailscale_tag`.

Hosts: converge to pick up the runtime; behaviour changes only in what
`platform deploy` refuses. An application whose health path does not answer
2xx/3xx — a NestJS service with a global prefix and no route at `/`, for
instance — must point `healthcheck.path` at a real endpoint before its next
deployment, or that deployment is rolled back.
