# Выжимка: вопросы и ответы по работе с платформой

Источник для будущей интерактивной документации. Собрано из рабочих диалогов
27–31 августа 2026: реальные вопросы оператора по ходу ввода платформы в строй,
ответы без воды. Три репозитория:

- **ядро** — `otostogan/platform-automation-core` (публичный): Ansible-коллекция
  `otostogan.platform` + Python-runtime `platform_automation`, релизится версиями.
- **инфра** — `ai-worldhub/platform-infra` (приватный): inventory, host_vars,
  пины ядра. Владеет тем, *что такое хосты*.
- **приложение** — например `ai-worldhub/health/client`: манифест `platform/v1`,
  compose, SOPS-секреты, свои workflows (build / release / deploy).

Живой пример хоста: `medkeep-host`, проект `health-client`, окружения `lab`
(dev-поддомен) и `production`.

## 1. Ключи и шифрование

**В: Где в инфре компании указываются публичные age-ключи?**
О: В `platform-infra/docs/RECIPIENTS.md` (таблица) и в `.sops.yaml` каждого
приложения (`creation_rules → key_groups → age`). Приватных половин в git нет
никогда.

**В: Зачем нужны age-ключи? Публичным шифруем, приватным расшифровываем?**
О: Да. SOPS шифрует секреты приложения на *публичные* получатели (recipients).
Сервер расшифровывает *приватным* ключом `/etc/platform/keys/age.key` — в tmpfs,
на диск открытый текст не попадает.

**В: Какие ключи генерить для первого сервера?**
О: Четыре сущности:

```bash
mkdir -p ~/.config/platform-keys && chmod 700 ~/.config/platform-keys
umask 077
age-keygen --output ~/.config/platform-keys/medkeep-host.agekey       # идентичность хоста
age-keygen --output ~/.config/platform-keys/medkeep-recovery.agekey   # escrow → в сейф компании
ssh-keygen -t ed25519 -f ~/.ssh/medkeep-ops -C "ops:<имя>"            # SSH оператора
```

Плюс SSH-ключ второго оператора (он генерит сам, отдаёт публичный).
`age-keygen -y <файл>` печатает публичный получатель из приватного ключа.

**В: Куда какой ключ едет? («все ключи что мы сделали и для чего»)**
О:

| Ключ | Приватная половина | Публичная половина |
| --- | --- | --- |
| host agekey | контроллер оператора → устанавливается на сервер в `/etc/platform/keys/age.key` | `.sops.yaml` каждого приложения + `RECIPIENTS.md` |
| recovery agekey | **только сейф компании** | те же два места |
| ops SSH (×2 оператора) | у каждого оператора | `users_ops_ssh_keys` в inventory |
| tailscale auth key | одноразовый файл `~/.config/platform-keys/tailscale-auth.key` | — |

Путь к приватному age-ключу — в git-игнорируемом
`inventory/host_vars/<host>/local-secrets.yml` (`secrets_age_key_source`),
к auth-key — в `inventory/group_vars/all/local-secrets.yml`
(`tailscale_auth_key_source`).

**В: agekey — для компании или для конкретного сервера?**
О: Для сервера. Второй хост обязан получить свой — иначе он сможет
расшифровать чужие секреты. Поэтому `secrets_age_key_source` лежит per-host,
а не в `group_vars/all`: новый хост без своего ключа падает громко.

**В: Мне все будущие ключи записывать в репозиторий инфры?**
О: Только публичные получатели — в `RECIPIENTS.md` и в `.sops.yaml`
приложений. Приватное — никогда: правило шире `.gitignore`.

**В: Recovery-ключ скопировать в сейф — а до этого его на сервер ставить?**
О: Нет. Recovery-ключ на сервер не едет вообще. Он существует, чтобы потеря
операторского ключа была переживаема: сейф → чистая машина → `sops decrypt`.

**В: Почему получателей два и что это даёт?**
О: `platform_cli_minimum_age_recipients: 2` (inventory) +
`minimum_age_recipients: 2` (вызов deploy-workflow). Ядро отказывает бандлу
с одним уникальным получателем на всех путях: сборка, деплой, роллбек,
восстановление секретов после ребута. Дубликат одного ключа не считается.

**В: Как приложение шифрует секреты?**
О: В репозитории приложения `.sops.yaml` с обоими получателями, затем:

```bash
sops encrypt --in-place deploy/secrets.lab.sops.yaml
```

Файл коммитится: это шифротекст, безопасно и намеренно.

## 2. Tailscale

**В: Не понял теги — как делать и для чего?**
О: Два вида, скоуп разный намеренно (`platform-infra/docs/TAILNET.md`):

- `tag:server-platform` — на каждом платформенном хосте, **общий по роли**.
  Десять хостов — один тег, один набор правил.
- `tag:ci-<project>` — на деплой-раннере одного репозитория приложения,
  **per-project**. Отвечает «чья автоматика подключилась», и позже позволяет
  сказать «CI medkeep может в прод, CI vibescan — нет».

Тег ещё решает владение: не-тегированное устройство принадлежит личному
аккаунту и его node key протухает — сервер тихо отваливается через месяцы.
Тегированное принадлежит тейлнету и не протухает.

**В: Новый сервер — надо редачить ACL?**
О: Нет. Выпустить auth key с `tag:server-platform`, добавить хост в
`inventory/hosts.yml`, bootstrap, converge. ACL правится только для нового
*приложения* (новый CI-тег: tagOwners + grants + ssh + tests) или для хоста
с *другим* уровнем доступа (изолированный прод → новый server-тег).

**В: Что могут CI и оператор?**
О: CI входит **только как `deploy`** и только на порт 22; sudoers `deploy`
разрешает ровно `platform deploy / status / rollback`. Оператор входит только
как `ops` под `action: check` (браузерное подтверждение, `checkPeriod` чтобы
Ansible не спрашивал на каждое соединение). Люди в политике не именуются —
только `autogroup:owner/admin`.

**В: Trust credential — что это и надо ли на каждый сервер?**
О: Это федеративная OIDC-идентичность для CI: GitHub Actions приложения
входит в тейлнет без хранимого ключа, по claim
`repo:ai-worldhub/health:ref:refs/heads/main` (привязан к репозиторию и ветке
`main`) с тегом `tag:ci-<project>`. Делается **per-project**, не per-server, и
не протухает как auth key. В workflow приложения:
`TS_OAUTH_CLIENT_ID`, `TS_AUDIENCE` (secrets), `PLATFORM_CI_TAILSCALE_TAG` (var).

**В: Auth key для сервера — какие настройки?**
О: Reusable off, **ephemeral off** (ephemeral-ноды удаляются при
отключении — правильно для CI-раннеров, смертельно для сервера), тег
`tag:server-platform`, минимальный срок. Он одноразовый и перезаписывается
перед каждым bootstrap, поэтому путь к нему общий в `group_vars/all`.

**В: Ограничение тегов?**
О: Теги контролируют доступ **к хосту**, не действия на нём. `deploy` общий, и
`platform deploy --project` принимает любой проект хоста. Проекты, которым
нельзя друг к другу, — это разные хосты, не разные теги.

## 3. Новый сервер: bootstrap → converge → readiness

Полная последовательность — `platform-infra/docs/BOOTSTRAP.md`. Скелет:

**В: `ansible-playbook: command not found`?**
О: Всё запускается из venv в корне инфры:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install 'ansible-core==2.15.13'
.venv/bin/ansible-galaxy collection install --force --requirement requirements.yml
```

**В: Bootstrap падает `Permission denied (publickey,password)`?**
О: Провайдер выдал пароль, Ansible ходит по ключу. Один раз вручную:

```bash
ssh-copy-id -i ~/.ssh/medkeep-ops.pub root@<адрес-провайдера>
ssh -i ~/.ssh/medkeep-ops root@<адрес> true   # не должен спросить пароль
```

Это единственный ручной SSH во всей последовательности.

**В: Что вместо `ansible_host: CHANGEME`?**
О: В `bootstrap.yml` — публичный IP провайдера. В `hosts.yml` — MagicDNS-имя
хоста в тейлнете (после handoff всё ходит через тейлнет).

**В: Порядок целиком?**
О:

```bash
.venv/bin/ansible-playbook otostogan.platform.bootstrap --inventory inventory/bootstrap.yml
# → хост в тейлнете; открыть НОВУЮ сессию ssh ops@<magicdns> и убедиться, что работает
.venv/bin/ansible-playbook otostogan.platform.converge --inventory inventory/hosts.yml
# второй converge обязан отчитаться нулём изменений
.venv/bin/ansible-playbook otostogan.platform.readiness --inventory inventory/hosts.yml
```

Консоль провайдера держать открытой до подтверждённого входа через тейлнет:
`access_guard` откажет конвергенции откуда-либо ещё, и это страховка, не баг.
После всего: ребут-приёмка (ребут → тейлнет вернулся → readiness → converge
с нулём изменений), затем снять публичный 22 порт и перевести
`proxy_acme_ca_uri` на боевой Let's Encrypt.

**В: `vps_readiness_phase` — где указывается и за что отвечает?**
О: `pre` — аудит самой машины (ОС, память, диск, маршруты), до конвергенции.
`post` — проверка построенного: юниты, Tailscale, UFW, docker-цепочки,
слушающие сокеты, прокси. Inventory компании пинит `post`, чтобы обычный
запуск был строгим без флага; на свежей машине:
`-e vps_readiness_phase=pre`.

**В: Converge упал на reboot_recovery entrypoint / повтор не сделал лишней работы?**
О: Идемпотентность — рабочий критерий: любой повторный converge обязан дать
`changed=0`. Если не даёт — это дефект, чинится в ядре, не обходится.

## 4. Как связаны репозитории и версии ядра

**В: Как инфра-репозиторий использует ядро?**
О: `requirements.yml` пинит релиз ядра по URL артефакта (`type: url`) —
версия является ревьюируемым изменением в git. Ядро публично, credential для
установки не нужен.

**В: Как обновить ядро на сервере? Почему команда не «сама подтянет версию»?**
О: Пин двигается руками — намеренно, никогда автоматически:

1. В `requirements.yml` поменять URL на новый тег.
2. `ansible-galaxy collection install --force --requirement requirements.yml`
   — `--force` обязателен: без него Galaxy оставит старую версию и отчитается
   успехом. Проверить: `ansible-galaxy collection list`.
3. `.venv/bin/ansible-playbook otostogan.platform.converge --inventory inventory/hosts.yml`
   и убедиться, что второй прогон — ноль изменений.

**В: Почему converge не в GitHub Actions?**
О: Конвергенции нужны age-ключ и вход `ops` — положить это в CI значит отдать
GitHub ключ от всех секретов и root на хосте. ACL пускает CI только как
`deploy` и только деплоить. Converge — с рабочей станции оператора.

**В: Зачем был CORE_FORBIDDEN_MARKERS / GitHub App / trust между приватными репо?**
О: Это всё была цена приватного ядра (кросс-репозиторные токены). Ядро стало
публичным — проблема исчезла целиком: релизы читаются анонимно, токен
`PLATFORM_CORE_TOKEN` и App не нужны. Trust credential Tailscale остался —
он про вход CI в тейлнет, не про доступ к коду.

## 5. Гит-флоу приложения

**В: В проектах только непонятные sha — можно версии как в ядре?**
О: Сделано. Схема (`health/client`):

1. Работаешь в `dev`, пушишь сколько угодно — **ничего не собирается**.
2. Готов выпуск → меняешь `version` в `package.json`, коммитишь.
3. `.githooks/post-commit` сам вешает **аннотированный** тег `v{version}`;
   в аннотацию попадают subject'ы всех коммитов с прошлой версии.
   `push.followTags` уносит тег со следующим пушем.
4. Тег `v*.*.*` триггерит `build.yml` (собирает и пушит image в ghcr; если
   image для этого коммита уже есть — переиспользует digest, не пересобирает)
   и `release.yml` (проверяет тег == package.json, публикует GitHub Release
   с текстом из аннотации тега).
5. `main` — чистая история релизов, стоит спокойно; `dev` доливается в него.

**В: `git tag v0.1.2 && git push origin v0.1.2` — закрепит на последний коммит?**
О: Да, тег указывает на HEAD в момент создания. Но руками больше не нужно —
хук делает это на бампе версии, и делает аннотированный тег (lightweight
release-workflow отвергает: в нём нет описания).

**В: Зачем main, если релизим тегами из dev?**
О: `main` — якорь: trust credential Tailscale привязан к
`refs:refs/heads/main`, там же живут файлы workflow, и он читается как чистая
история выпусков. Ритуал «релиз доезжает до main» — открытый пункт (см. §12).

## 6. Деплой

**В: Как задеплоить?**
О: В репозитории приложения → Actions → **Deploy** → Run workflow:

- `environment`: `lab` | `production`
- `ref`: версия / ветка / коммит; **пусто = последний GitHub Release**
  (намеренно не head ветки — «что сейчас на main» это путь незарелизенной
  работы в прод).
- `label`: необязательное имя записи в реестре (и цель роллбека).

Workflow сам резолвит коммит в digest образа (платформа деплоит только по
digest и отвергает тег), собирает бандл (метаданные + манифест + compose +
секреты, ровно 4 файла), входит в тейлнет как `tag:ci-<project>` и выполняет
`platform deploy` на хосте под пользователем `deploy`.

**В: В каком окружении actions собирают image?**
О: `ubuntu-24.04` GitHub-hosted runners — обычные 4 vCPU машины. Сборка
кэшируется buildx'ом, а одинаковый коммит вообще не пересобирается.

**В: Куда смотреть на хосте?**
О:

```bash
sudo -n platform status --project health-client --environment lab --json
```

Отвечает: текущий релиз (id, tag, digest, статус, healthcheck, миграция),
последняя попытка, бэкапы (свежайший дамп, когда восстановимость доказана,
окно потери, состояние offsite).

**В: Порядок деплоя с базой?**
О: База поднята и здорова → (дамп перед миграцией) → миграции → приложение.
База, которая не поднялась, роняет деплой до того, как что-либо переключилось
и до записи в реестр.

## 7. Роллбек и ретенция образов

**В: Как делать роллбек? Хочу через деплой.**
О: Основной путь — тот же Deploy workflow со старой версией в `ref`. Реестр
ведёт честную прямую историю: роллбек записывается как новый деплой. Повторный
деплой уже текущей версии — no-op (`containers_started: false`).

Аварийный путь (CI/registry/сеть недоступны) — на хосте, из уже лежащих
артефактов:

```bash
sudo -n platform rollback \
  --project <project> --environment <environment> \
  --to <previous-release-tag> \
  --registry-username <user> --registry-token-stdin --json
```

Отказывает, пока какой-то релиз висит в `deploying` — исход миграции
неизвестен, гвард не обходить.

**В: Роллбек и данные?**
О: **Роллбек не откатывает данные.** Он двигает назад приложение; том базы
переживает деплои, роллбеки и ретенцию. Это самое вероятное неверное
предположение об этой системе.

**В: Где указывается retained_releases? Считается как?**
О: `deployment.retained_releases` в манифесте приложения (по умолчанию 5,
максимум 50). Считается по **различным image digest**, не по деплоям:
передеплой одной версии десять раз не выселяет версии позади неё. Digest
удаляется только когда его не хочет ни один ledger на хосте — lab и prod
одного приложения штатно крутят один digest. Записи реестра не чистятся
никогда — только staged-бандл и кэш образа.

**В: Есть ли смысл указывать retained_releases в обоих окружениях?**
О: Да, независимо: у lab и prod разные паттерны. Lab churn'ится каждым пушем и
не откатывается — хватает 2; prod держит глубину офлайн-роллбека.

**В: `docker system prune` для уборки?**
О: Никогда на платформенном хосте: прокси и ACME-компаньон живут в том же
демоне. Уборка — только ретенция ядра, после коммита реестра, и она умеет
только предупреждать.

## 8. База данных

**В: Хочу для каждого окружения свой контейнер БД — реализуемо?**
О: Реализовано. Приложение объявляет в манифесте:

```yaml
database:
    mode: docker
    postgres_major: 18
    backup_enabled: true
    backup:
        interval_minutes: 15
        retain: 3
restore_validation:
    query: SELECT 1
```

Платформа сама: генерит compose в
`/var/lib/platform/databases/{project}/{environment}/`, пинит образ по digest
(TOFU — резолвится один раз до смены мажора), создаёт именованный том на пару
проект+окружение, включает контейнер в отдельную **internal** сеть
(`platform-db-{project}-{environment}`), портов наружу нет ни в одном
окружении. Compose приложения подключается через
`${PLATFORM_DB_NETWORK:?}`.

**В: Только приложение знает пароль базы? Мы его нигде не указываем?**
О: Никто не указывает. Пароль генерится при первом деплое, хранится
SOPS-зашифрованным рядом с compose базы (на те же получатели + escrow) и
подмешивается в окружение приложения как `DATABASE_URL`. Приложение,
приносящее свой `DATABASE_URL`, получает отказ.

**В: Можем ли проебать пароль? Последствия?**
О: Потеря пароля — не потеря данных. Образ доверяет локальному сокету:
оператор с root делает `docker exec` в контейнер, `psql` без пароля, ставит
новый, перешифровывает креденшл. Есть и команда:

```bash
sudo -n platform rotate-database-password \
  --project <p> --environment <e> --confirm-disruptive --json
```

Порядок намеренный: сначала база, потом креденшл, потом рестарт приложения.
Невосполним только том — на это и бэкапы.

**В: Смена postgres_major?**
О: На существующем томе — отказ: данные сами между мажорами не переезжают
(а 18-я ещё и сменила раскладку внутри тома). Официальный путь — дамп →
удалить том → восстановить в новый мажор. Второй гвард: том есть, а
креденшл-файл пропал — тоже отказ, не генерация нового пароля. Существующий
том священен.

**В: Как подключиться через pgAdmin?**
О: Прямо — никак, и это дизайн: сеть internal, портов нет. Честные пути:
`ssh ops@<host>` → `docker exec -it <db-контейнер> psql -U app`, либо
осознанный временный туннель. «Туннель к базе с автоснятием» — кандидат в
команды будущего оператор-CLI (§13).

**В: Сколько приложений/окружений можно на один хост?**
О: Сколько угодно: compose-проект — `{project}-{environment}`, у каждого свой
манифест `platform.<env>.yml`, свой реестр, своя база, свой таймер бэкапов.
lab и production medkeep на одном хосте — рабочая конфигурация.

## 9. Бэкапы

**В: Снять дамп руками / посмотреть все бэкапы?**
О:

```bash
sudo -n platform backup  --project <p> --environment <e> --json
sudo -n platform backups --project <p> --environment <e>        # таблица, newest first
```

`pg_dump` (custom-формат) идёт потоком через `age` — открытый текст существует
только в пайпе. Шифруется на тех же получателей, что секреты, escrow включая:
бэкап наследует общий bus factor, а не заводит свой.

**В: Как прочитать мету дампа `20260829T...-operator.dump.age`?**
О: В имени намеренно только время и причина (`operator|schedule|pre-migration`).
Всё остальное — карточка метаданных (release_id, тег, digest, мажор, размер,
checksum): она лежит и файлом-спутником `.card.json`, и **внутри**
зашифрованного потока (конверт `PLATFORM-BACKUP/1 <len>` перед байтами
pg_dump):

```bash
age --decrypt -i /etc/platform/keys/age.key <дамп> | head -c 800
```

Старые дампы без конверта читаются по-прежнему. Версия приложения в имя
объекта не попадает намеренно: ключи S3 читаемы любым, кто умеет листинг.

**В: Восстановление?**
О:

```bash
sudo -n platform restore --project <p> --environment <e> \
  --from <stamp> --confirm-destructive --json
```

Без `--from` — самый свежий. Отказывает под деплой-локом. Дамп с другого
релиза — предупреждение, не запрет (иногда именно это и нужно, но схема живёт
в дампе). Доказательство восстановимости:

```bash
sudo -n platform verify-backup --project <p> --environment <e> --json
```

Одноразовый контейнер `--network none --rm`, прогон `restore_validation.query`,
снос в `finally`; каждая попытка записывается — `platform status` отвечает
«когда восстановимость последний раз *доказана*», а не «когда сняли дамп».

**В: Расписание — как обновить тайминги и как смотреть?**
О: Тайминги живут в манифесте (`backup.interval_minutes`), доезжают обычным
деплоем: деплой реконсилирует drop-in таймера
`platform-backup@{project}-{environment}.timer`. Отключение backup_enabled /
уход на внешнюю базу снимает таймер. Смотреть:

```bash
systemctl list-timers 'platform-backup@*'
journalctl --unit 'platform-backup@*' --since today
```

Таймеры монотонные: выключенный хост не доигрывает пропущенное, просто
продолжает. `platform status` показывает окно потери; когда свежайший дамп
старше двух интервалов — говорит «расписание встало».

**В: Дамп перед миграцией?**
О: Автоматический, не гейтится на `backup_enabled` (флаг — про расписание, не
про страховку разрушительного шага). Это единственное «хозяйственное»
действие, которое **роняет деплой**: нет сетки — нет прыжка.

## 10. S3 / offsite

**В: Какие переменные нужны и где?**
О: Не-секреты — открыто в `inventory/group_vars/platform_hosts.yml`:

```yaml
platform_cli_offsite_enabled: true
platform_cli_offsite_endpoint: https://s3.example.com   # endpoint провайдера
platform_cli_offsite_region: <регион>
platform_cli_offsite_bucket: <бакет>
```

Секрет — только пара ключей: путь в git-игнорируемом
`host_vars/<host>/local-secrets.yml`
(`platform_cli_offsite_credentials_source: ~/.config/platform-keys/...s3.env`,
файл `0600`); на хосте становится `/etc/platform/keys/s3.env`. Раскладка в
бакете: `{хост}/{проект}/{окружение}/`.

**В: Один бакет на сервер?**
О: Один бакет на **платформу**, префикс на хост первым уровнем. Граница IAM ==
граница префикса: новый проект на том же хосте не требует правки политики.
Переопределяется в host_vars одной строкой, когда понадобится другой
регион/аккаунт.

**В: Ядро ставит awscli на сервер?**
О: Нет. Выгрузка — через `python3-boto3` из apt (SigV4). awscli ставили только
локально, для проверки бакета руками.

**В: Бэкапы копились локально 5 недель, потом подключили S3 — перекидывать?**
О: Само: выгрузка **реконсилирует, а не пушит** — каждый прогон уносит всё,
чего нет в бакете. Включение offsite поднимает существующие дампы первым же
прогоном; вчерашняя упавшая выгрузка ретраится сегодня; объём ограничен
локальной ретенцией.

**В: Права хоста в бакете?**
О: **Только запись**: `PutObject` + `ListBucket` строго под условием
`s3:prefix` (без условия ListBucket на ARN бакета позволил бы листать чужие
префиксы — изоляция была бы фикцией). Удалять хост не может: удалением
занимается lifecycle-правило бакета + версионирование + Object Lock. Бэкап,
который атакующий может стереть, защищает только от отказа диска.

**В: Провал выгрузки?**
О: Единственное место, где правило «только предупреждения» гнётся: провал
выгрузки **роняет команду** — молча переставший выгружать хост находят слишком
поздно. Сам дамп при этом успешен и остаётся локально до следующего прогона.
`platform status` показывает: `current` / `behind` / `not-configured`.

**В: Восстановление из бакета, когда локального дампа нет?**
О: Ключ на чтение — операторский, подаётся на stdin, на хост не попадает:

```bash
cat ~/.config/platform-keys/reader-s3.env |
  sudo -n platform restore --project <p> --environment <e> \
    --from <stamp> --from-offsite --confirm-destructive --json
```

`--from` обязателен: «самого свежего» нет, когда пропала именно локальная копия.

**В: Terraform для бакета?**
О: Решили полумеру: IAM-политику и lifecycle-JSON закоммитить в
`platform-infra/aws/` как ревьюируемые документы, без Terraform-стейта.
(Ещё не сделано — см. §12.)

## 11. Bus factor

**В: Что за проблема bus factor = 1 и как решена?**
О: Система не должна умирать с одним человеком. Закрыто по слоям:

- **Секреты**: два age-получателя обязательны машинно; recovery-ключ в сейфе,
  протестирован с чистой машины.
- **Доступ**: два ключа в `users_ops_ssh_keys`, два владельца тейлнета,
  провайдер-аккаунт компанейский.
- **Ядро**: публичный репозиторий — компания не зависит от личных доступов;
  форк + PR как путь исправлений.
- **Бэкапы**: шифруются на тот же набор с escrow — читает их тот же круг, что
  и секреты.
- Ритуал: квартальная учение второго оператора (runbook, §Quarterly drill).

Открыто (блокируется административно, не кодом): компанейский AWS-аккаунт с
двумя админами, второй read-only IAM-пользователь, и главная проверка фазы 6 —
второй оператор восстанавливает lab по одному только runbook своими ключами.

- **`platform-infra/aws/`** с IAM/lifecycle JSON — ещё не закоммичено.
- **Административное**: компанейский AWS-аккаунт, второй IAM-reader,

- **PITR** — намеренно не сейчас; дизайн оставил место (`backup.strategy`,
  раскладка префиксов под архив журнала, платформа владеет конфигом постгреса).

## 13. После готовности платформы (целевые задачи)

1. **Эталонная интерактивная документация** — одна страница, отвечающая на
   любой вопрос целиком: каждый кейс (деплой, откат, восстановление,
   подключение к базе, новый проект, новый оператор, новый хост) пошагово,
   с копируемыми командами и картой зависимостей процессов. Runbook,
   BOOTSTRAP, TAILNET, RECIPIENTS становятся её источниками, не заменой.
   Настоящий документ — сырьё для неё.
2. **CLI оператора поверх platform-infra** — запускается в каталоге инвентаря,
   сам понимает контекст (хосты, проекты, окружения) и даёт полную картину
   одной командой. Кандидаты: статус по всем хостам, пароль базы, туннель к
   базе с автоснятием, дрейф пинов. Ключевой открытый вопрос — граница работы
   с секретами (расшифровка локально vs на хосте) — продумать до кода.
